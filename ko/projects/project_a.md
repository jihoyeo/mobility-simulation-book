# 기말 프로젝트 — 내가 사는 동네의 대중교통

개인 과제입니다. 6주차에 시작해 12주차에 발표합니다. 성적의 40%입니다.

## 무엇을 하는가

자기가 사는 동네를 하나 골라, 그 지역의 대중교통을 시뮬레이션하고 **개선안 하나의 효과를 숫자로 제시**합니다.

이런 결론이 나오면 됩니다.

> 하남시 미사동에서 오전 8시에 출발하는 통행의 중앙값 통행시간은 42분이고, 그중 14분이 대기시간이다. 미사강변도시를 지나는 30번 버스의 배차간격을 12분에서 8분으로 줄이면 중앙값이 38분으로 4분 줄어든다. 대신 필요한 차량이 5대에서 8대로 늘어난다.

숫자 뒤에 근거가 있고, 대가가 무엇인지 함께 적혀 있는 것이 목표입니다.

## 왜 이 과제인가

교재 6~7장에서 만든 RAPTOR 는 하남 데이터로만 돌려 봤습니다. 자기가 아는 동네로 옮겨 보면 두 가지가 드러납니다.

첫째, 데이터가 생각대로 생기지 않았습니다. 정류장 이름이 두 가지로 들어오고, 노선이 경계에서 끊기고, 새벽에 한 번만 다니는 노선이 평균을 망칩니다.

둘째, **자기가 매일 타는 노선이라 검증이 됩니다.** 시뮬레이션이 "이 구간 20분"이라고 하는데 실제로는 35분 걸린다고 해 봅시다. 어디가 틀렸는지 물을 수 있습니다. 하남 데이터로는 이 감각이 생기지 않습니다.

## 대상지 고르기

전국 시군구 경계가 저장소에 들어 있습니다.

```python
from smartmob.data import list_sigungu, sigungu_info

list_sigungu("성남")          # ['성남시']
sigungu_info("하남시")        # 면적 92.8 km², 경계 좌표
```

```{note}
특별시·광역시는 통짜 폴리곤 하나입니다. 서울시를 고르면 정류장이 만 개가 넘어 계산이 무거워집니다. 인구 20만~50만 규모의 시·군이 다루기 좋습니다. 서울에 산다면 자치구 경계를 직접 그리거나(geojson.io) 인접 경기도 시를 고르세요.
```

도로망까지 필요한 분석(택시 시뮬레이션)을 하려면 서버에 준비된 도시여야 합니다. 대중교통만 다루면 GTFS 만 있으면 되므로 어느 시군구든 됩니다. 대부분의 학생은 후자로 충분합니다.

## 6주차 — 대상지 정하기

경계를 정하고 저장합니다.

```python
import json
from shapely.geometry import mapping
from smartmob.data import load_sigungu, sigungu_info

boundary = load_sigungu("하남시")
print(sigungu_info("하남시"))

with open("boundary.geojson", "w", encoding="utf-8") as f:
    json.dump(mapping(boundary), f)
```

`01_scope.md` 에 적을 것: 대상지 이름, 면적, 인구(통계청), 고른 이유, 그 지역에서 평소 불편하다고 느낀 것 하나.

마지막 항목이 나중에 개선 시나리오가 됩니다.

## 8주차 — GTFS 자르기 (HW3)

전국 GTFS 를 내려받아 대상지만 남깁니다. 5장에서 한 것과 같습니다.

```python
from smartmob.data import ensure
from smartmob.data.gtfs import load_gtfs_feed, clip_to_boundary, describe_feed, save_gtfs

zip_path = ensure("GTFS_Korea_2024.zip")     # 처음 한 번만 내려받습니다
feed = load_gtfs_feed(zip_path)
mine = clip_to_boundary(feed, boundary, buffer_m=500)

describe_feed(mine)
save_gtfs(mine, "gtfs/")
```

`02_gtfs.md` 에 적을 것:

- 자르기 전후의 정류장·노선·운행 수
- `route_type` 분포표 (5장의 TAGO 코드로 해석)
- 첫차와 막차 시각
- **이상해 보이는 것 하나.** 정류장 이름 중복, 운행이 하루 한 번뿐인 노선, 좌표가 엉뚱한 정류장 등

마지막 항목이 배점에 들어갑니다. 데이터를 들여다봤는지가 여기서 드러납니다.

## 9주차 — 분석할 통행 정하기

O-D 100쌍을 정합니다. 무작위로 뽑아도 되지만, 의미 있는 기준으로 고르면 결론이 강해집니다.

- 주거지에서 그 지역 최대 고용지(시청·산업단지·대학)로
- 각 행정동 중심에서 가장 가까운 지하철역으로
- 8장의 O-D 데이터에서 통행량 상위 100쌍

```python
from smartmob.teaching.raptor import TransitData

data = TransitData.from_gtfs(mine)
origins = data.access_stops(위도, 경도)
```

`03_demand.md` 에 적을 것: 100쌍을 어떻게 골랐는지, 출발 시각을 몇 시로 잡았는지와 그 근거.

## 11주차 — 현재 상태 재기

각 O-D 를 자기 RAPTOR 로 계산하고 지표를 뽑습니다.

```python
from smartmob.teaching.raptor import raptor, journey, summarize
from smartmob.teaching.fare import calc_fare

rows = []
for o, d, dep in od_pairs:
    result = raptor(data, data.access_stops(*o), dep)
    legs = journey(data, result, data.nearest_stop(*d))
    s = summarize(data, legs, dep)
    if s.get("reachable"):
        s["fare"] = calc_fare(legs)
        rows.append(s)
```

**엔진과 대조합니다.** 서버가 있으면 같은 O-D 를 `dt.transit_route()` 로 물어 나란히 놓습니다. 서버가 없으면 10쌍을 직접 지도 앱에서 검색해 비교합니다. 손으로 열 번 확인하는 것도 검증입니다.

`04_baseline.md` 에 적을 것:

- 통행시간·차내시간·도보·대기·환승·요금 여섯 지표의 분포 (중앙값·90분위·최댓값)
- 대조표: 자기 계산 vs 엔진(또는 지도 앱). 차이가 큰 쌍 3개와 그 이유
- 12장에서 배운 대로 평균과 함께 분포를 보입니다

## 12주차 — 개선안과 발표

6주차에 적은 "불편한 것"을 시나리오로 만듭니다. 세 가지 중 하나면 됩니다.

| 시나리오 | 무엇을 고치나 | GTFS 에서 |
|---|---|---|
| 배차간격 단축 | 특정 노선의 운행 편수를 늘림 | `trips.txt` + `stop_times.txt` 에 운행 추가 |
| 노선 신설 | 없던 구간을 잇는 노선 추가 | `routes.txt` 에 노선, 정류장 순서와 시각표 작성 |
| 정류장 이설·신설 | 정류장을 옮기거나 추가 | `stops.txt` 좌표 수정, `stop_times.txt` 반영 |

고친 GTFS 로 같은 100쌍을 다시 계산하고 before-after 를 비교합니다.

**대가를 반드시 적습니다.** 배차간격을 줄이면 차량이 더 필요합니다. 노선을 신설하면 운영비가 듭니다. 개선만 적고 비용을 적지 않은 보고서는 감점입니다.

## 평가 (100점)

| 항목 | 배점 | 무엇을 보나 |
|---|---|---|
| 데이터 준비 | 20 | 자르기가 맞는가. 데이터의 이상한 점을 찾아냈는가 |
| 경로 탐색 정확도 | 20 | 자기 RAPTOR 가 도는가. 엔진·지도 앱과 대조했는가 |
| 시나리오 설계 | 20 | 실현 가능한가. 왜 그 개선인지 근거가 있는가 |
| 지표 해석 | 25 | 분포를 봤는가. 대가를 함께 적었는가. 한계를 밝혔는가 |
| 발표와 재현성 | 15 | 8분에 전달되는가. 코드를 받아 다시 돌릴 수 있는가 |

### 감점

- 서비스율 없이 평균 대기시간만 보고 (12장 생존 편향)
- 개선 효과만 적고 비용·대가를 적지 않음
- 한계 절이 없음. 무엇을 가정했고 무엇을 넣지 않았는지 밝히지 않음
- 코드가 다시 돌아가지 않음. 절대 경로, 손으로 고친 중간 파일

### 가점

- 실제로 그 노선을 타 보고 시뮬레이션 결과와 비교
- 지도 앱과 10쌍 이상 대조하고 차이의 원인을 규명
- 자기 지역 데이터에서만 나오는 문제를 찾아내고 해결

## 자주 막히는 곳

**전국 GTFS 가 큽니다.** 압축을 풀면 몇 GB 입니다. `load_gtfs_feed` 는 필요한 표만 읽지만 그래도 메모리를 씁니다. 노트북이 버거우면 `stop_times.txt` 를 청크로 읽어 대상 `trip_id` 만 남기세요.

자른 뒤 정류장이 너무 적습니다. 버퍼를 500m 에서 1km 로 늘려 보고, 그래도 적으면 대상지가 좁은 것입니다. 인접 시군을 포함하거나 대상지를 바꿉니다.

RAPTOR 가 아무 데도 못 갑니다. 출발 시각이 운행 시간 밖일 가능성이 큽니다. 첫차·막차를 먼저 확인하세요. `calendar.txt` 의 운행일도 봅니다.

통행시간이 비현실적으로 짧습니다. 도보 환승이 직선거리 기반이라 강이나 철길을 무시합니다. 6.4절의 경고를 보고서 한계 절에 적으세요.
