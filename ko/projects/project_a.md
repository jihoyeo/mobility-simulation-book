# 기말 프로젝트 — 가천대 교내셔틀 무당이 시뮬레이션과 개선 분석

개인 과제이며 take-home 시험입니다. 6주차에 시작해 12주차에 보고서를 냅니다. 발표는 없습니다. 성적의 40%입니다.

## 무엇을 하는가

가천대 글로벌캠퍼스 교내셔틀 무당이의 현황을 여러분이 만든 데이터와 여러분이 짠 경로 탐색기로 재현합니다. 그 위에서 개선 시나리오 하나의 효과를 숫자로 제시합니다.

이런 결론이 나오면 됩니다.

> 1교시 직전 30분에 가천대역 정류장에서 승차하는 학생의 대기시간 중앙값은 6분, 90분위는 14분이다. 배차간격을 10분에서 6분으로 줄이면 90분위가 8분으로 줄지만 차량이 3대에서 5대로 늘어난다.

숫자 뒤에 근거가 있고, 대가가 무엇인지 함께 적혀 있는 것이 목표입니다.

## 왜 이 과제인가

교재 6~7장의 RAPTOR 와 11장의 루프는 하남 데이터로만 돌려 봤습니다. 매일 타는 셔틀로 옮기면 두 가지가 드러납니다.

첫째, 데이터가 없습니다. 무당이 GTFS 는 어디에도 없으므로 5장에서 읽기만 하던 형식을 직접 씁니다. 승하차 인원도 없으므로 직접 셉니다. 데이터를 만들어 보면 형식이 왜 그렇게 생겼는지가 남습니다.

둘째, 답을 검증할 수 있습니다. 시뮬레이션이 "평균 4분 대기"라고 하는데 실제로 10분씩 기다린다면, 모형의 어느 가정이 틀렸는지 물을 수 있습니다.

셔틀 수요는 교시에 묶여 극단적으로 몰립니다. 11.8절의 "배차 알고리즘은 수요가 공급을 압박할 때만 의미가 있다"가 여기서 확인됩니다.

## 과업

모든 과업을 개인이 수행합니다. 현장 조사는 여럿이 같은 시간에 시간대와 정류장을 나눠 봐도 되지만, 조사표와 GTFS 와 분석은 각자 만들고 각자 냅니다.

1. 현황 데이터 구축: 정류장·노선 GeoJSON, 무당이 GTFS, 승하차 조사표
2. 기준 시나리오 재현: 조사표로 수요 프로파일을 만들고 자기 RAPTOR 로 현황 통행시간 계산
3. 개선 시나리오 하나: 사전·사후 비교와 대가

| 시나리오 | 무엇을 바꾸나 | 어디를 고치나 |
|---|---|---|
| 배차간격 조정 | 특정 시간대의 운행 편수 | `trips.txt`, `stop_times.txt` |
| 노선·정류장 변경 | 정차 순서, 정류장 이설·신설 | `stops.txt`, `stop_times.txt` |
| 차량 대수·정원 변경 | 투입 차량 수 또는 정원 | 시뮬레이션 입력 |
| DRT 전환 | 저수요 시간대를 호출형으로 | 11장 루프 |
| 시간대별 차등 운행 | 첨두·비첨두 배차를 다르게 | `trips.txt`, `stop_times.txt` |

## 6주차 — 정류장과 노선

무당이가 서는 정류장 전부와 노선별 정차 순서를 GeoJSON 으로 만듭니다. 좌표는 지도 앱의 핀이 아니라 실제로 버스가 서는 지점입니다. 두 곳이 20m 넘게 차이 나면 도보 환승 계산이 어긋납니다.

순환 노선이면 기점과 종점을 어디로 볼지 정하고 근거를 적습니다. 같은 정류장에 양방향 정차면 `stop_id` 를 나눌지 합칠지 정합니다. 합치면 방향을 구분할 수 없고, 나누면 조사표도 나눠 세야 합니다.

시나리오 카드에 "평소 불편했던 것" 하나를 적어 둡니다. 언제, 어느 정류장에서, 무엇이. 이것이 12주차 시나리오가 됩니다.

## 8주차 — GTFS 와 승하차 조사

5장에서 읽기만 하던 GTFS 를 직접 씁니다. `stops`, `routes`, `trips`, `stop_times`, `calendar` 다섯 표입니다.

```
routes.txt      무당이 노선
trips.txt       배차간격만큼 반복되는 운행들
stop_times.txt  각 운행이 각 정류장에 서는 시각
stops.txt       정류장
calendar.txt    운행일
```

정류장 사이 소요시간은 3장의 최단경로로 구하고 정차시간(정류장당 20~30초)을 더합니다. 캠퍼스가 언덕이라 실제로는 더 걸립니다. 오르막 구간에 계수를 곱하고 그 사실을 적으세요. 운행 간격은 관찰값을 쓰고, 관찰하지 못한 시간대는 추정값임을 문서에 남깁니다.

`route_type` 은 국제 표준이 아니라 TAGO 코드를 씁니다(5.2절). 시작 코드가 `starter/02_fixed_route.py` 에 있습니다.

```python
from smartmob.data import load_gtfs_feed, validate_feed, describe_feed

feed = load_gtfs_feed("gtfs/")
validate_feed(feed)
print(describe_feed(feed))
```

승하차 조사는 정류장별·시간대별로 승차 인원과 하차 인원을 셉니다. 30분 단위로, 최소 세 구간(1교시 직전, 점심, 저녁 하교)을 봅니다. 정류장 여러 곳을 같은 시간대에 봐야 하므로 여럿이 나눠 관측하고 원자료를 공유해도 됩니다. 조사표는 각자 만들고, 함께 조사한 사람과 각자 맡은 정류장·시간대를 적습니다.

| 열 | 뜻 |
|---|---|
| `stop_id`, `stop_name` | 정류장 |
| `date`, `time_bin` | 조사일, 30분 구간 |
| `boardings`, `alightings` | 승차, 하차 인원 |
| `source` | `observed` 또는 `estimated` |

관측하지 못한 시간대를 추정해서 채워도 됩니다. 다만 `source` 로 구분해야 합니다. 구분하지 않으면 감점입니다.

만든 GTFS 를 자기 RAPTOR 에 넣고 O-D 세 건을 시간표와 손으로 대조합니다. 정류장 수와 패턴 수를 함께 출력합니다. 패턴 수가 운행 수와 같으면 정류장 순서가 같은 운행이 묶이지 않은 것입니다(6.2절).

## 9주차 — 수요 프로파일과 현황 재현

조사표를 8.4절의 수요 형식으로 바꿉니다. 정류장별·시간대별 승차 인원이 그 시간대의 호출 건수입니다. 8장의 `generate_demand` 는 도로망 위에 흩뿌리는 방식이라 그대로 쓸 수 없습니다. 셔틀 수요는 정해진 정류장 사이를 오갑니다. 시작 코드가 `starter/01_class_demand.py` 에 있습니다. 교시 시간표만으로 수요를 만드는 코드이므로, 조사표의 승차 인원을 읽어 쓰도록 고칩니다.

수요를 만들 때 정할 것이 셋입니다. 셋 다 가정이고 보고서에 전부 적습니다.

1. 몇 명인가 — 조사표의 승차 인원. 조사하지 못한 시간대는 교시 시간표로 보간
2. 언제인가 — 교시 시작 시각 앞으로 퍼뜨립니다. 관찰값이 있으면 그것을 씁니다
3. 어디서 어디로 — 정류장별 승차·하차 비율

`validate_demand` 를 통과시킵니다. 분과 초, 위도와 경도가 뒤바뀐 것을 여기서 잡습니다.

현황 시뮬레이션은 자기 RAPTOR 로 O-D 별 통행시간을 구하는 것입니다. 12장 지표 표(서비스율, 대기 중앙값·90분위, 통행시간 분포)로 냅니다. DRT 전환 시나리오를 골랐다면 11장 루프도 준비합니다.

## 12주차 — 시나리오 분석과 보고서

자기 시나리오로 GTFS 또는 시뮬레이션 입력을 고치고, 같은 O-D 100건과 같은 수요로 다시 계산해 사전·사후를 비교합니다.

배차간격·차량 대수 시나리오는 `starter/03_sweep.py` 로 여러 값을 훑고 12.4절의 파레토 프론트를 그립니다. seed 를 3회 이상 반복합니다. 11장 루프는 결정론적이고 난수는 수요 생성에 있으므로, seed 마다 수요를 새로 만들어야 반복 실험이 됩니다.

DRT 전환 시나리오는 11장 루프를 씁니다. 셔틀은 여러 명을 함께 태우는데 11장 루프는 한 명씩 태웁니다. 정원을 반영하려면 배차 로직을 고쳐야 합니다. 어렵다면 정원 1로 두고 그 한계를 보고서에 적어도 됩니다.

**대가를 반드시 적습니다.** 배차간격을 줄이면 차량이 더 필요합니다. 정류장을 옮기면 걷는 사람이 생깁니다. 개선만 적고 비용을 적지 않은 보고서는 감점입니다.

## 자주 막히는 곳

패턴 수가 운행 수와 같습니다. 정류장 순서가 같은 운행이 묶이지 않은 것입니다. `stop_sequence` 가 운행마다 1부터 증가하는지, 순환 노선에서 같은 정류장이 두 번 나올 때 행이 둘인지 확인합니다.

수요가 너무 적어 시나리오 간 차이가 안 납니다. 11.8절대로, 배차 방법은 수요가 공급을 압박할 때만 차이가 납니다. 첨두 30분만 따로 보세요. 차량을 줄여 압박을 만들면 차이가 드러납니다.

참조 구현과 몇 초씩 어긋납니다. 도보 속도와 우회 계수를 먼저 확인합니다. 24시를 넘는 시각은 `parse_gtfs_time` 으로 다룹니다.

조사한 요일이 하루뿐입니다. 그것이 한계입니다. 한계 절에 적으면 감점하지 않습니다. 적지 않으면 감점합니다.

정원을 어떻게 넣나요. 차량마다 `capacity` 를 두고, 배차할 때 남은 자리만큼만 태웁니다. 전부 구현하기 어려우면 범위를 줄이고 한계를 적으세요. 못 한 것을 적는 것이 대충 한 것보다 낫습니다.
