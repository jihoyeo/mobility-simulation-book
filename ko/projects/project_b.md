정규 수업에서 만든 시뮬레이터를 그대로 씁니다. 새로 배우는 것은 없고, 배운 것을 실제 문제에 붙입니다.

## 무엇을 하는가

가천대 글로벌캠퍼스 셔틀 노선을 설계하고, 정해진 노선과 수요응답 방식 중 어느 쪽이 나은지를 같은 수요 위에서 비교합니다.

최종 결론은 이런 모양입니다.

> 1교시 직전 30분 수요 480명에 대해, 15인승 6대로 5분 간격 고정노선을 운영하면 평균 대기 4.2분·서비스율 98%다. 같은 6대를 수요응답으로 돌리면 평균 대기 6.8분·서비스율 91%로 나빠진다. 첨두에는 고정노선이 낫다. 반면 저녁 7시 이후 수요 40명 구간에서는 수요응답이 평균 대기 3.1분으로 고정노선(7.5분)을 이긴다.

"어느 쪽이 무조건 낫다"가 아니라 **"언제 어느 쪽이 낫다"** 가 답입니다.

## 왜 이 문제인가

셔틀버스는 두 가지 점에서 좋은 연습입니다.

수요가 극단적으로 몰립니다. 교시 시작 15분 전에 거의 모든 통행이 일어납니다. 11.8절에서 "배차 알고리즘은 수요가 공급을 압박할 때만 의미가 있다"고 했는데, 여기가 정확히 그 상황입니다. 하남 택시 시나리오에서는 드러나지 않던 차이가 보입니다.

답을 검증할 수 있습니다. 여러분이 매일 타는 셔틀입니다. 시뮬레이션이 "평균 4분 대기"라고 하는데 실제로 10분씩 기다린다면, 모형의 어느 가정이 틀렸는지 물을 수 있습니다.

## 1주차 — 수요 만들기

셔틀 수요는 택시 수요와 다릅니다. 시간이 교시에 묶여 있고, 목적지가 캠퍼스 하나입니다.

배포 자료를 씁니다.

```python
import pandas as pd

stops = pd.read_csv("projects/b_campus_shuttle/data/candidate_stops.csv")
schedule = pd.read_csv("projects/b_campus_shuttle/data/class_schedule.csv")
stops.head()
```

`candidate_stops.csv` 는 캠퍼스 반경 1.3km 안의 실제 정류장 27곳입니다. 성남 GTFS 에서 뽑았고 `daily_trips` 는 그 정류장의 하루 운행 편수입니다. 공급이 이미 많은 곳과 적은 곳을 구분하는 데 씁니다.

```{warning}
`class_schedule.csv` 는 **예시 값**입니다. 실제 교시 시간을 학사일정에서 확인해 고치세요. 이 값이 틀리면 첨두 시각이 통째로 어긋납니다.
```

수요를 만들 때 정할 것이 셋입니다.

1. **몇 명인가** — 학과별 정원과 시간표에서 추정합니다. 가정을 전부 적으세요
2. **언제인가** — 교시 시작 시각을 기준으로 앞뒤로 퍼뜨립니다. 정규분포로 두어도 되고, 실제 관찰값이 있으면 그것을 씁니다
3. **어디서 오는가** — 가천대역·복정역·태평역에서 오는 비율. `daily_trips` 가 힌트가 됩니다

8장의 `generate_demand` 를 그대로 쓸 수는 없습니다. 그건 도로망 위에 흩뿌리는 방식입니다. 셔틀 수요는 정해진 몇 지점 사이를 오갑니다. 시작 코드가 `starter/01_class_demand.py` 에 있습니다.

기준선은 셔틀이 없을 때입니다. 학생들이 걸어 올라가거나 시내버스를 탑니다. 6장의 RAPTOR 로 계산하거나, 도보 시간만 계산해도 됩니다.

## 2주차 — 두 방식 비교

### 고정노선

노선을 정하고 시간표를 만들어 GTFS 로 씁니다. 5장에서 읽기만 하던 형식을 이번에는 **직접 씁니다.**

```
routes.txt      셔틀 노선 하나
trips.txt       배차간격만큼 반복되는 운행들
stop_times.txt  각 운행이 각 정류장에 서는 시각
stops.txt       고른 정류장들
```

정류장 사이 소요시간은 3장의 최단경로로 구합니다. 거기에 정차 시간(정류장당 20~30초)을 더합니다.

만든 GTFS 를 자기 RAPTOR 에 넣으면 학생들의 통행시간이 나옵니다.

### 수요응답

11장의 시뮬레이션 루프를 그대로 씁니다. 정류장이 아니라 호출 지점에서 태웁니다.

```python
from smartmob.teaching.simloop import simulate

run = simulate(demand, vehicles, time_start=..., time_end=...)
run.summary()
```

한 가지 손봐야 합니다. 셔틀은 여러 명을 함께 태웁니다. 11장 루프는 한 명씩 태웁니다. 정원을 반영하려면 배차 로직을 고쳐야 합니다. 가장 단순한 방법은 같은 방향 승객을 묶어 한 번에 배차하는 것입니다. 어렵다면 정원 1로 두고 그 한계를 보고서에 적어도 됩니다.

### 비교

같은 수요, 같은 차량 대수로 두 방식을 돌리고 12장의 지표로 비교합니다.

```python
from smartmob.teaching.metrics import compare

compare({"고정노선": fixed_run, "수요응답": drt_run})
```

시간대를 나눠 보세요. 첨두와 비첨두에서 결과가 뒤집힐 가능성이 큽니다. 그게 이 프로젝트의 답입니다.

## 3주차 — 스윕과 파레토

파라미터를 바꿔 가며 훑습니다.

| 파라미터 | 값 |
|---|---|
| 차량 대수 | 2, 3, 4, 6 |
| 배차간격(고정노선) | 5분, 10분, 15분 |
| 정원 | 15인승, 25인승 |
| 난수 seed | 3회 반복 |

4 × 3 × 2 × 3 = 72회입니다. 자기 루프로 돌리면 시나리오당 1초 미만이므로 한 번에 끝납니다. 서버로 돌리면 팀 컨테이너 하나에 직렬로 들어가므로 오래 걸립니다. 자기 루프로 훑고, 최종안 몇 개만 서버로 확인하세요.

seed 3회 반복이 중요합니다. 한 번만 돌린 결과의 차이가 진짜 차이인지 난수 때문인지 구분할 수 없습니다.

12.4절의 파레토 프론트를 그립니다. 가로축은 서비스율(또는 평균 대기), 세로축은 차량-시간(운영비 대리 지표)입니다.

### 감점

- 서비스율 없이 대기시간만 제시
- seed 한 번만 돌린 결과로 시나리오 우열 주장
- 실제로 버스가 못 다니는 경로(계단, 보행자 전용로)를 노선으로 제시
- 첨두와 비첨두를 나누지 않고 하나의 결론만 제시

### 가점

- 실제 셔틀 운행을 관찰해 수요 추정을 검증
- 정원 제약을 제대로 넣은 수요응답 구현
- 두 방식을 섞은 안(첨두 고정노선 + 비첨두 수요응답)을 설계하고 효과를 보임

## 자주 막히는 곳

수요 추정에 자신이 없습니다. 정확할 필요는 없습니다. **가정을 명시하고 민감도를 보이면** 됩니다. "학생 1,000명이 셔틀을 탄다고 가정했고, 500명이나 2,000명일 때 결론이 바뀌는지 확인했다"가 좋은 보고입니다.

정류장 사이 소요시간을 모르겠습니다. 3장의 최단경로로 구합니다. 캠퍼스가 언덕이라 실제로는 더 걸립니다. 오르막 구간에 계수를 곱하고 그 사실을 적으세요.

정원을 어떻게 넣나요. 차량마다 `capacity` 를 두고, 배차할 때 남은 자리만큼만 태웁니다. 태운 승객의 목적지가 같으면 함께 갑니다. 전부 구현하기 어려우면 범위를 줄이고 한계를 적으세요. 못 한 것을 적는 것이 대충 한 것보다 낫습니다.

결과가 시시합니다. 차이가 안 나면 수요가 너무 적거나 차량이 너무 많은 것입니다. 차량을 줄여 압박을 만들면 방식 간 차이가 드러납니다. 11.8절에서 본 그대로입니다.
