# P-실무프로젝트 — 내가 사는 동네의 버스 노선 개선

종강 후 3주간 진행합니다. 평일 10:00–12:00, AI공학관 210호. 최종발표는 12월 11일입니다.

정규 수업과 기말 프로젝트에서 만든 분석 절차를 그대로 씁니다. 새로 배우는 것은 없고, 배운 것을 새로운 지역에 붙입니다.

## 무엇을 하는가

자기가 사는 동네(시군구 하나)를 골라 그 지역의 버스 노선을 시뮬레이션하고, 개선 후보안 여러 개의 효과와 대가를 숫자로 비교합니다.

이런 결론이 나오면 됩니다.

> 하남시 미사동에서 오전 8시에 출발하는 통행의 중앙값 통행시간은 42분이고, 그중 14분이 대기시간이다. 미사강변도시를 지나는 30번 버스의 배차간격을 12분에서 8분으로 줄이면 중앙값이 38분으로 4분 줄어든다. 대신 필요한 차량이 5대에서 8대로 늘어난다. 같은 차량 3대를 신설 노선에 쓰면 중앙값은 40분이지만 도달 가능한 O-D 가 12쌍 는다.

노선망 설계 솔버를 만드는 것이 아닙니다. 후보안을 사람이 만들고, 시뮬레이션으로 평가하고, 파레토 프론트에서 고릅니다.

## 왜 이 문제인가

기말 프로젝트의 무당이는 정류장 열 개 남짓의 작은 시스템이었습니다. 시군구 하나로 옮기면 두 가지가 달라집니다.

첫째, 데이터가 생각대로 생기지 않았습니다. 정류장 이름이 두 가지로 들어오고, 노선이 경계에서 끊기고, 새벽에 한 번만 다니는 노선이 평균을 망칩니다. 5장에서 하남으로 한 번 해 본 일을 낯선 데이터로 다시 합니다.

둘째, 자기가 매일 타는 노선이라 검증이 됩니다. 시뮬레이션이 "이 구간 20분"이라고 하는데 실제로는 35분 걸린다면 어디가 틀렸는지 물을 수 있습니다.

## 1주차 — 대상지와 데이터

전국 시군구 경계가 저장소에 들어 있습니다.

```python
from smartmob.data import list_sigungu, sigungu_info

list_sigungu("성남")          # ['성남시']
sigungu_info("하남시")        # 면적 92.8 km², 경계 좌표
```

```{note}
특별시·광역시는 통짜 폴리곤 하나입니다. 서울시를 고르면 정류장이 만 개가 넘어 계산이 무거워집니다. 인구 20만~50만 규모의 시·군이 다루기 좋습니다. 서울에 산다면 자치구 경계를 직접 그리거나(geojson.io) 인접 경기도 시를 고르세요.
```

전국 GTFS 를 내려받아 대상지만 남깁니다. 5장에서 한 것과 같고, 시작 코드가 `starter/01_clip_gtfs.py` 에 있습니다.

```python
from smartmob.data import ensure
from smartmob.data.gtfs import load_gtfs_feed, clip_to_boundary, describe_feed, save_gtfs

zip_path = ensure("GTFS_Korea_2024.zip")     # 처음 한 번만 내려받습니다
feed = load_gtfs_feed(zip_path)
mine = clip_to_boundary(feed, boundary, buffer_m=500)

describe_feed(mine)
save_gtfs(mine, "gtfs/")
```

`01_scope.md` 에 적을 것: 대상지 이름, 면적, 인구, 고른 이유, 그 지역에서 평소 불편하다고 느낀 것 하나. 마지막 항목이 3주차 후보안이 됩니다.

`02_demand.md` 에 적을 것:

- 자르기 전후의 정류장·노선·운행 수와 `route_type` 분포표(TAGO 코드로 해석)
- 첫차와 막차 시각
- **이상해 보이는 것 하나.** 정류장 이름 중복, 운행이 하루 한 번뿐인 노선, 좌표가 엉뚱한 정류장 등. 이 항목이 배점에 들어갑니다
- O-D 100쌍과 고른 기준. 8장의 수도권 생활이동 O-D 에서 통행량 상위 쌍을 쓰거나, 각 행정동 중심에서 최대 고용지·가장 가까운 역으로 잡습니다
- 출발 시각과 그 근거

## 2주차 — 현재 상태와 후보안

각 O-D 를 자기 RAPTOR 로 계산하고 지표를 뽑습니다. 시작 코드가 `starter/02_baseline.py` 에 있고, O-D 를 고르는 부분이 빈칸입니다.

```python
from smartmob.teaching.raptor import TransitData, raptor, journey, summarize
from smartmob.teaching.fare import calc_fare

data = TransitData.from_gtfs(mine)
rows = []
for o, d, dep in od_pairs:
    result = raptor(data, data.access_stops(*o), dep)
    legs = journey(data, result, data.nearest_stop(*d))
    s = summarize(data, legs, dep)
    if s.get("reachable"):
        s["fare"] = calc_fare(legs)
        rows.append(s)
```

**엔진과 대조합니다.** 서버가 있으면 같은 O-D 를 `dt.transit_route()` 로 물어 나란히 놓습니다. 서버가 없으면 10쌍을 직접 지도 앱에서 검색해 비교합니다. 손으로 열 번 확인하는 것도 검증입니다.

`03_baseline.md` 에 적을 것:

- 통행시간·차내시간·도보·대기·환승·요금 여섯 지표의 분포(중앙값·90분위·최댓값)
- 대조표: 자기 계산 vs 엔진(또는 지도 앱). 차이가 큰 쌍 3개와 그 이유
- 후보안 목록. 둘 이상. 1주차에 적은 불편함에서 출발합니다

| 후보안 | 무엇을 고치나 | GTFS 에서 |
|---|---|---|
| 배차간격 단축 | 특정 노선의 운행 편수를 늘림 | `trips.txt` + `stop_times.txt` 에 운행 추가 |
| 노선 신설·연장 | 없던 구간을 잇는 노선 추가 | `routes.txt` 에 노선, 정류장 순서와 시각표 작성 |
| 정류장 이설·신설 | 정류장을 옮기거나 추가 | `stops.txt` 좌표 수정, `stop_times.txt` 반영 |
| 저수요 노선 DRT 전환 | 운행 편수가 적은 노선을 호출형으로 | 노선을 빼고 11장 루프로 같은 수요를 처리 |

## 3주차 — 평가와 파레토

후보안마다 GTFS 를 고쳐 `gtfs_scenario_*/` 로 저장하고, 같은 O-D 100쌍을 다시 계산합니다. 시작 코드가 `starter/03_scenario.py` 에 있고, 고치는 부분이 빈칸입니다.

후보안마다 두 값을 냅니다. 개선 효과(통행시간 중앙값 감소, 도달 가능 O-D 증가)와 대가(추가 차량-시간). 이 두 축으로 12.4절의 파레토 프론트를 그립니다. 곡선이 꺾이는 지점을 보이고, 어느 안을 왜 고르는지 적습니다. 데이터가 답을 정해 주지 않습니다.

DRT 전환 주제는 11장 루프로 고정노선과 같은 수요를 돌리고 seed 를 3회 이상 반복합니다. 난수는 수요 생성에 있으므로 seed 마다 수요를 새로 만듭니다.

**대가를 반드시 적습니다.** 배차간격을 줄이면 차량이 더 필요합니다. 노선을 신설하면 운영비가 듭니다. 개선만 적고 비용을 적지 않은 보고서는 감점입니다.

| 경로 탐색 정확도 | 20 | 자기 RAPTOR 가 도는가. 엔진·지도 앱과 대조했는가 |
| 후보안 설계 | 20 | 둘 이상인가. 실현 가능한가. 왜 그 개선인지 근거가 있는가 |
| 지표 해석 | 25 | 분포를 봤는가. 파레토로 비교했는가. 대가와 한계를 적었는가 |
| 발표와 재현성 | 15 | 15분에 전달되는가. 코드를 받아 다시 돌릴 수 있는가 |

항목별 체크리스트는 `projects/b_neighborhood_transit/rubric.md` 에 있습니다.

### 감점

- 서비스율 없이 평균 대기시간만 보고 (12장 생존 편향)
- 개선 효과만 적고 비용·대가를 적지 않음
- 후보안이 하나뿐
- 한계 절이 없음
- 코드가 다시 돌아가지 않음. 절대 경로, 손으로 고친 중간 파일

### 가점

- 실제로 그 노선을 타 보고 시뮬레이션 결과와 비교
- 지도 앱과 10쌍 이상 대조하고 차이의 원인을 규명
- 자기 지역 데이터에서만 나오는 문제를 찾아내고 해결

## 자주 막히는 곳

전국 GTFS 가 큽니다. 압축을 풀면 몇 GB 입니다. `load_gtfs_feed` 는 필요한 표만 읽지만 그래도 메모리를 씁니다. 노트북이 버거우면 `stop_times.txt` 를 청크로 읽어 대상 `trip_id` 만 남기세요.

자른 뒤 정류장이 너무 적습니다. 버퍼를 500m 에서 1km 로 늘려 보고, 그래도 적으면 대상지가 좁은 것입니다. 인접 시군을 포함하거나 대상지를 바꿉니다.

RAPTOR 가 아무 데도 못 갑니다. 출발 시각이 운행 시간 밖일 가능성이 큽니다. 첫차·막차를 먼저 확인하세요. `calendar.txt` 의 운행일도 봅니다.

통행시간이 비현실적으로 짧습니다. 도보 환승이 직선거리 기반이라 강이나 철길을 무시합니다. 6.4절의 경고를 보고서 한계 절에 적으세요.

후보안 간 차이가 시시합니다. 개선한 노선을 지나는 O-D 만 따로 보세요. 100쌍 전체 중앙값에는 묻히는 차이가 해당 축에서는 뚜렷할 수 있습니다. 그 사실 자체가 결론의 일부입니다.
