# 1장 왜 시뮬레이션인가

0장에서 하남시 택시 80대로 저녁 6시부터 자정까지 시뮬레이션을 실행했습니다. 평균 대기시간은 4.1분이었지만 차량 가동률은 27%에 그쳤습니다. 승객에게는 괜찮은 서비스처럼 보이고, 운영자에게는 차량이 너무 많은 것처럼 보입니다.

그렇다면 80대는 적정한 수일까요? 40대로 줄이면 대기시간은 얼마나 늘어나고, 서비스를 받지 못하는 승객은 몇 명이나 생길까요? 실제 운영에서는 두 대안에 동일한 호출과 통행시간을 적용할 수 없습니다. 시뮬레이션에서는 차량 수만 바꿔 두 운영안을 비교할 수 있습니다.

이 장에서는 좋은 모빌리티 시스템을 무엇으로 판단하는지, 왜 실제 운영 대신 시뮬레이션이 필요한지 봅니다. 그다음 80대 결과를 평균 대신 분포로 다시 읽고, 이 책에서 만들 시뮬레이터의 네 단계를 훑습니다.

## 학습 목표

- 실제 운영만으로 여러 운영안을 공정하게 비교하기 어려운 이유를 설명합니다
- VISSIM·SUMO와 이 책에서 만들 시뮬레이터의 해상도 차이를 설명합니다
- 평균과 분포, 승객과 운영자 지표를 함께 보고 다음 실험을 정합니다
- 시뮬레이터의 네 단계와 각 장의 관계를 설명합니다

## 1.1 좋은 모빌리티 시스템이란

모빌리티 시스템은 사람과 물건이 이동하는 데 쓰는 수단과 운영 체계를 말합니다. 지하철과 버스, 택시, 자전거와 전동킥보드, 배달 오토바이와 보행이 여기에 포함됩니다.

무엇이 좋은 시스템인지는 누구에게 묻느냐에 따라 다릅니다.

- **승객**은 빨리 오고 빨리 가기를 바랍니다. 대기시간과 통행시간이 짧아야 합니다.
- **운영자**는 차를 놀리고 싶지 않습니다. 차량 한 대가 하루에 몇 명을 태웠는지가 중요합니다.
- **도시**는 도로가 막히지 않고 배기가스가 적기를 바랍니다.

셋은 서로 부딪힙니다. 차를 많이 넣으면 대기시간은 줄지만 빈 차가 늘고, 도로에는 차가 더 늘어납니다.

그래서 차량을 10대 늘렸을 때 대기시간과 빈 차량 수가 각각 얼마나 달라지는지 함께 계산해야 합니다.

12장에서는 승객·운영자·도시의 관점에서 이 지표들을 계산합니다.

## 1.2 왜 시뮬레이션이 필요한가

한 가지 방법은 서비스 차량 80대를 저녁 6시부터 자정까지 실제로 운행하는 것입니다. 하지만 한 번 운행해서 얻은 기록은 차량 80대와 선택한 배차 규칙의 결과만 보여 줍니다. "40대였으면 어땠을까", "차고지를 두 곳으로 나눴으면" 같은 질문에는 답하기 어렵습니다.

대안끼리 비교하려면 같은 여섯 시간을 조건만 바꿔 다시 관찰해야 하는데, 실제 도시에서는 그렇게 할 수 없습니다.

시뮬레이션은 이 반복 관찰을 계산으로 대신합니다. 이 책의 모형은 시간을 1분 간격으로 진행하며 차량 위치와 승객 상태를 기록합니다. 차량 수를 80대에서 40대로 바꿔 다시 돌리면, 같은 수요와 도로망에서 두 운영안의 대기시간을 비교할 수 있습니다.

이 비교 결과는 모형에 넣은 수요와 통행시간을 전제로 합니다. 호출 시각이나 통행시간이 실제와 다르면 대기시간도 달라집니다. 8장에서는 수요를 만들고, 9장에서는 통행시간 모형을 점검합니다.

### 이미 있는 도구를 쓰면 되지 않는가

교통 시뮬레이터는 이미 여럿 있습니다. 차량 한 대가 차로 위 어디에 있는지까지 계산하는 도구가 있고, 이 책처럼 어느 교차로에 있는지만 계산하는 도구가 있습니다. 이 차이를 해상도라고 부르겠습니다. 어느 쪽을 쓸지는 무엇을 물을 것인가에 달렸습니다.

```{figure} ../figures/vissim.png
:name: fig-vissim
:width: 90%

VISSIM 화면. 교차로 하나를 차로 단위로 그리고, 차량마다 위치를 개별로 계산합니다.
```

{numref}`fig-vissim` 은 교차로에서 차량마다 차로 위 위치를 계산한 화면입니다. VISSIM(독일 PTV)과 AIMSUN(스페인 TSS)은 차량의 차간거리와 차로 변경을 시간 단위별로 계산하는 미시 교통류 시뮬레이터입니다. "이 교차로의 좌회전 신호를 5초 늘리면 대기행렬이 몇 미터 줄어드는가" 같은 질문을 분석할 수 있습니다.

차량의 세밀한 움직임을 계산할수록 입력 자료와 계산량도 늘어납니다. VISSIM과 AIMSUN은 상용 도구이므로 수강생이 코드를 열어 배차 과정의 각 단계를 구현하는 이 책의 실습에도 맞지 않습니다.

SUMO(독일 DLR)는 오픈소스 미시 교통류 시뮬레이터입니다. TraCI 인터페이스로 실행 중인 차량을 파이썬에서 제어할 수 있고, 수요응답형 교통도 모의할 수 있습니다. 이 책의 질문에도 사용할 수 있지만, 기본 모형은 차로 위에서 움직이는 차량을 계산합니다. 여기서는 차로 변경보다 호출 발생, 배차, 차량 이동의 관계를 직접 구현하는 데 초점을 둡니다.

이 책의 모형은 차량이 차로 안에서 어떻게 움직이는지는 생략합니다. 대신 차량이 몇 시 몇 분에 어느 노드에 있는지 기록하고, 수강생이 배차 규칙을 코드로 바꿔 다시 실행할 수 있게 만듭니다.

직접 만든다고 해도 전부 새로 만드는 것은 아닙니다. 재료는 이미 공개되어 있습니다. 도로망은 OpenStreetMap에서 받습니다(2장). 최단경로는 직접 짠 다익스트라로 구합니다(3장). 대중교통 시간표는 GTFS라는 공개 표준을 씁니다(5장).

이 자료를 이용해 호출 발생, 배차, 차량 이동을 처리하는 시뮬레이션 코드를 작성합니다.

## 1.3 차량 80대는 적정한가

0장에서 실행한 하남시 택시 80대의 결과를 더 자세히 살펴봅니다.

```{code-cell} python
from smartmob import Dtumos

dt = Dtumos()
sim = dt.run_simulation(
    city="hanam", mode="taxi", fleet_size=80, num_passengers=1000,
    time_start=1080, time_end=1440, random_seed=42,
)
sim.summary()
```

`Dtumos` 가 클래스이고 `sim` 이 결과 객체라는 것은 0.4절의 상자에서 봤습니다. 이 장의 실습에서 두 객체가 무엇을 담고 있는지 직접 확인합니다.

호출 990건이 전부 배차됐고 평균 대기시간은 4.1분입니다. 평균만 보면 승객이 오래 기다리지 않은 것처럼 보입니다.

그런데 평균만 보면 놓치는 것이 있습니다. 승객별 대기시간의 분포를 봅니다.

```{code-cell} python
wait = sim.passengers["wait_min"]
for q in [0.5, 0.9, 0.95]:
    print(f"{q:>5.0%} 분위  {wait.quantile(q):5.1f}분")
print(f"최댓값     {wait.max():5.1f}분")
```

절반은 3분 안에 탔지만, 스무 명 중 한 명은 11분 넘게 기다렸고 가장 오래 기다린 사람은 41분이었습니다. 평균 4.1분이라는 숫자 하나로는 이 사람이 보이지 않습니다.

차량 쪽도 봅니다. 0장의 `sim.record` 는 차량을 빈 차와 운행 중인 차 둘로만 나눴습니다. `sim.result` 는 운행 중인 차를 승객을 태운 차와 태우러 가는 차로 다시 나눕니다.

```{code-cell} python
r = sim.result
print(f"승객 태운 차량 평균  {r['occupied_vehicle_num'].mean():.1f}대")
print(f"데리러 가는 차량 평균 {r['dispatched_vehicle_num'].mean():.1f}대")
print(f"빈 차 평균          {r['empty_vehicle_num'].mean():.1f}대")
```

시간대별로 승객을 태우고 있던 차량은 평균 10대, 태우러 가는 차량은 평균 4대, 빈 차량은 평균 31대였습니다. 셋을 더해도 80대가 안 되는 것은 0.5절에서 본 대로 근무 시간이 끝난 차량이 빠지기 때문입니다.

차량을 절반으로 줄이면 평균 대기시간과 오래 기다리는 승객 수는 어떻게 달라질까요? 990건 중 배차되지 못한 호출이 생기는지도 확인합니다.

이 질문에 답하려면 같은 수요와 같은 도로망에서 차량 40대로 다시 돌려 봐야 합니다. 실제 운영에서는 불가능하고, 시뮬레이터에서는 인자 하나를 바꾸면 됩니다.

다만 이 책의 녹화본에는 80대짜리 결과만 들어 있습니다. 40대로 바꿔 돌리려면 DTUMOS 서버가 필요하고, 서버를 띄우는 방법은 부록 B에 있습니다.

## 1.4 시뮬레이터의 구조

우리가 만들 시뮬레이터는 네 단계로 나뉩니다.

```{figure} ../figures/ch01_framework.png
:name: fig-framework
:width: 85%

시뮬레이터의 네 단계. 데이터를 넣어 모형을 보정하고, 그 위에서 서비스를 운영한 뒤, 결과를 지표와 그림으로 냅니다.
```

{numref}`fig-framework` 은 데이터 준비, 모형 보정, 서비스 운영, 결과 분석의 네 단계를 보여 줍니다. 서비스 운영 단계는 수요와 차량 생성, 재배치, 배차, 차량 이동으로 다시 나뉩니다. 이 책에서 다루는 구성요소와 장의 관계는 다음과 같습니다.

| 그림의 부분 | 하는 일 | 다루는 장 |
|---|---|---|
| 데이터(Data) | 도로망, 대중교통 시간표, 과거 통행 기록을 준비합니다 | 2장, 5장, 8장 |
| 보정(Calibration) | 두 지점 사이의 통행시간을 계산하거나 예측합니다 | 3~4장, 9장 |
| 수요·공급 생성기(Demand & Supply Generator) | 호출이 발생하는 시각과 위치, 차량의 수와 초기 위치를 정합니다 | 8장 |
| 배차 알고리즘(Dispatch Algorithm) | 호출이 겹쳤을 때 어느 차량을 보낼지 정합니다 | 10~11장 |
| 차량 라우터(Vehicle Router) | 도로망을 따라 차량 위치를 갱신합니다 | 3~4장 |
| 결과(Outputs) | 대기시간과 차량 상태를 계산하고 그림으로 나타냅니다 | 12장 |

차량 재배치 알고리즘(Vehicle Relocation Algorithm)은 이 책에서 다루지 않습니다. 빈 차를 수요가 많은 곳으로 미리 옮기는 문제인데, 배차와 수요 예측을 둘 다 알아야 손댈 수 있습니다. 프로젝트 B에서 여유가 있는 팀이 도전할 만한 주제입니다.

배차 알고리즘은 각 차량이 승객에게 도착하는 데 몇 분이 걸리는지 알아야 합니다. 이 값을 예상 도착시간(ETA, estimated time of arrival)이라고 합니다. 직선거리만 쓰면 강 건너에 있는 차량을 가장 가깝다고 잘못 고를 수 있습니다. 3장에서는 도로망의 최단경로로, 9장에서는 과거 통행 기록으로 학습한 모형으로 ETA를 구합니다.
